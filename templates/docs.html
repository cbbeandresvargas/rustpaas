{{ t.nav_docs }} — {{ app_name }}

{{ app_name }} es una plataforma como servicio (PaaS) personal construida en Rust. Despliega cualquier aplicación que compile a un binario standalone — Rust, Go, C, o cualquier otro lenguaje — sin dependencias externas pesadas. Un solo proceso gestiona el dashboard, la API REST, el proxy inverso y un motor S3 embebido.

Toda la persistencia vive en un directorio raíz configurable (por defecto /var/lib/mypaas/). Para migrar o hacer backup del PaaS entero, basta con copiar esa carpeta.

Autenticación

La API de {{ app_name }} acepta dos métodos de autenticación:

  • Sesión web — cookie rustpaas_session generada al hacer login en el dashboard.
  • API Key (Bearer Token) — cabecera Authorization: Bearer <tu-api-key>. La clave se genera automáticamente al crear tu cuenta y es visible en el dashboard.

Para scripts o CI/CD usa siempre el Bearer Token. La API key tiene el prefijo paas_sk_ seguido de 32 caracteres hexadecimales.

curl -X POST https://paas.tudominio.com/api/deploy \
  -H "Authorization: Bearer paas_sk_abc123..." \
  -F "name=mi-app" \
  -F "binary=@./mi-app"

Deploy Manual (curl)

Compila tu aplicación para la arquitectura del servidor (normalmente x86_64-unknown-linux-gnu) y envía el binario al endpoint POST /api/deploy:

# Compilar
cargo build --release --target x86_64-unknown-linux-gnu

# Desplegar
curl -X POST https://paas.tudominio.com/api/deploy \
  -H "Authorization: Bearer $PAAS_API_KEY" \
  -F "name=mi-app" \
  -F "binary=@./target/x86_64-unknown-linux-gnu/release/mi-app"

{{ app_name }} asignará un puerto libre, configurará el subdominio mi-app.paas.tudominio.com, creará un bucket S3 dedicado y arrancará el proceso inyectando las variables de entorno automáticamente.

Respuesta exitosa (HTTP 201)

{
  "project_id": "uuid-...",
  "name": "mi-app",
  "port": 8101,
  "pid": 12345,
  "message": "Deployed successfully"
}

Bundle Deploy (Binario + Assets)

Si tu aplicación necesita archivos adicionales junto al binario — una carpeta public/ con HTML/CSS/JS, plantillas, imágenes u otros recursos estáticos — puedes subir todo empaquetado en un tar.gz. El sistema lo detecta automáticamente por sus magic bytes y lo extrae antes de arrancar el proceso.

Transparente para la API: El endpoint POST /api/deploy es el mismo. La única diferencia es que envías un .tar.gz en lugar de un binario plano. La detección es automática.

¿Cómo funciona?

  • El bundle se extrae en {data_dir}/apps/{nombre}/workspace/
  • El proceso se arranca desde esa carpeta como directorio de trabajo (CWD)
  • Tu app puede leer sus assets con rutas relativas: ./public/index.html
  • El binario debe llamarse igual que el proyecto (o ser el único ejecutable en el tar)

Crear el bundle localmente

# Compilar
cargo build --release --target x86_64-unknown-linux-gnu

# Empacar binario + carpeta public/ en un tar.gz
tar -czf bundle.tar.gz \
  -C ./target/x86_64-unknown-linux-gnu/release mi-app \
  -C ../../.. public/

# Desplegar el bundle (mismo endpoint, misma llamada)
curl -X POST https://paas.tudominio.com/api/deploy \
  -H "Authorization: Bearer $PAAS_API_KEY" \
  -F "name=mi-app" \
  -F "binary=@bundle.tar.gz"
Consejo: Si tu binario sirve archivos estáticos, asegúrate de que use rutas relativas al CWD o lee la variable APP_NAME para detectar su entorno. El proceso siempre arranca desde la carpeta workspace.

Deploy Automatizado (GitHub Actions)

Añade este archivo a tu repositorio en .github/workflows/deploy.yml y configura el secreto PAAS_API_KEY en los settings del repositorio. El workflow soporta tanto deploy de binario solo como bundle con assets:

name: Deploy to {{ app_name }}
on:
  push:
    branches: [main]

env:
  PROJECT_NAME: "mi-app"
  RUSTPAAS_URL: "https://paas.tudominio.com"
  # BUNDLE_ASSETS: "public"  # Descomenta para bundle deploy con carpeta assets

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: Swatinem/rust-cache@v2
      - uses: dtolnay/rust-toolchain@stable
        with:
          targets: x86_64-unknown-linux-gnu

      - name: Build
        run: cargo build --release --target x86_64-unknown-linux-gnu

      # Opción A: solo el binario
      - name: Deploy binary
        if: ${{ "{{" }} !env.BUNDLE_ASSETS {{ "}}" }}
        run: |
          curl -sf -X POST "$RUSTPAAS_URL/api/deploy" \
            -H "Authorization: Bearer ${{ "{{" }} secrets.PAAS_API_KEY {{ "}}" }}" \
            -F "name=$PROJECT_NAME" \
            -F "binary=@./target/x86_64-unknown-linux-gnu/release/$PROJECT_NAME"

      # Opción B: bundle (binario + assets en tar.gz)
      - name: Deploy bundle
        if: ${{ "{{" }} env.BUNDLE_ASSETS {{ "}}" }}
        run: |
          tar -czf bundle.tar.gz \
            -C ./target/x86_64-unknown-linux-gnu/release "$PROJECT_NAME" \
            $BUNDLE_ASSETS
          curl -sf -X POST "$RUSTPAAS_URL/api/deploy" \
            -H "Authorization: Bearer ${{ "{{" }} secrets.PAAS_API_KEY {{ "}}" }}" \
            -F "name=$PROJECT_NAME" \
            -F "binary=@bundle.tar.gz"

Rollback

Cada vez que haces un redeploy, {{ app_name }} guarda un snapshot del binario (o bundle) anterior. Se mantienen los últimos 3 deploys por proyecto. Puedes revertir desde el dashboard (sección Historial de Deploys) o vía API:

# Listar deploys anteriores
curl -H "Authorization: Bearer $PAAS_API_KEY" \
  https://paas.tudominio.com/api/projects/{id}/deploys

# Revertir a un deploy específico
curl -X POST -H "Authorization: Bearer $PAAS_API_KEY" \
  https://paas.tudominio.com/api/projects/{id}/rollback/{deploy_id}

Variables de Entorno Inyectadas

Cuando {{ app_name }} arranca tu binario, inyecta automáticamente las siguientes variables de entorno. Tu aplicación puede leerlas con std::env::var, dotenvy, o cualquier biblioteca equivalente:

VariableEjemploDescripción
DATABASE_URL sqlite:///var/lib/mypaas/apps/mi-app/data/app.db SQLite de tu app, listo para SQLx o rusqlite
S3_ENDPOINT http://127.0.0.1:18101 S3 privado de tu proyecto (puerto = tu puerto + 10 000)
S3_BUCKET bucket-mi-app Nombre del bucket creado automáticamente
AWS_ACCESS_KEY_ID uuid-del-proyecto Credencial de acceso al S3 privado
AWS_SECRET_ACCESS_KEY uuid-secreto Clave secreta del S3 privado
AWS_REGION us-east-1 Región fija (requerida por los SDKs de S3)
PORT 8101 Puerto en el que tu app debe escuchar
APP_NAME mi-app Nombre del proyecto
⚠️ PORT no se puede sobrescribir. El proxy inverso enruta el tráfico al puerto asignado; si tu app escucha en otro puerto, las peticiones no llegarán.

Variables de Entorno Personalizadas

Desde la página de detalle de un proyecto en el dashboard puedes editar un archivo .env con variables adicionales. Estas se inyectan después de las variables del sistema, por lo que pueden sobrescribir cualquiera excepto PORT.

Casos de uso habituales: credenciales de terceros, configuración de la app, activar modo debug, o apuntar el S3 a un bucket externo de AWS en lugar del local.

# Ejemplo de .env personalizado
SECRET_KEY=supersecret
STRIPE_KEY=sk_live_...
AWS_ACCESS_KEY_ID=AKIAIOSFODNN7EXAMPLE   # sobrescribe el S3 local
AWS_SECRET_ACCESS_KEY=wJalrXUtnFEMI/...
S3_ENDPOINT=https://s3.amazonaws.com
S3_BUCKET=mi-bucket-en-aws

Al guardar los cambios, el dashboard reinicia el proceso automáticamente para aplicarlos.

Almacenamiento S3 Integrado

Cada proyecto desplegado tiene su propio servidor S3 aislado (basado en s3s-fs). El servidor se inicia junto con el proceso de tu app y se detiene cuando esta se suspende o para.

Detalles técnicos

  • El S3 escucha en 127.0.0.1:{PORT + 10000} — si tu app usa el puerto 8101, su S3 está en el 18101.
  • Las credenciales son únicas por proyecto y se generan automáticamente. Están disponibles en las variables AWS_ACCESS_KEY_ID y AWS_SECRET_ACCESS_KEY.
  • Los archivos se almacenan en el sistema de archivos del servidor en /var/lib/mypaas/storage/buckets/{project_id}/.

Uso con aws-sdk-s3 (Rust)

use aws_sdk_s3::Client;
use aws_config::BehaviorVersion;

let endpoint = std::env::var("S3_ENDPOINT").unwrap();
let bucket   = std::env::var("S3_BUCKET").unwrap();

let config = aws_config::defaults(BehaviorVersion::latest())
    .endpoint_url(&endpoint)
    .load()
    .await;

let client = Client::new(&config);
client.put_object()
    .bucket(&bucket)
    .key("archivo.txt")
    .body(/* bytes */)
    .send()
    .await?;
Nota: El S3 privado solo es accesible desde 127.0.0.1. Si quieres exponer archivos públicamente, sirve los ficheros directamente desde tu app o usa un bucket externo de AWS sobreescribiendo las variables desde el panel de entorno.

SQLite & Backups

Para datos transaccionales, {{ app_name }} recomienda SQLite. Tu app corre siempre en la misma máquina y sistema de archivos, lo que garantiza que la ruta de DATABASE_URL siempre es válida.

Uso con SQLx

// Lee la URL inyectada por {{ app_name }}
let db_url = std::env::var("DATABASE_URL")
    .unwrap_or_else(|_| "sqlite://./dev.db".to_string());

let pool = sqlx::SqlitePool::connect(&db_url).await?;

Backups en vivo

Desde el dashboard, el botón Descargar Backup (DB) ejecuta VACUUM INTO sobre la base de datos de tu app, generando una copia consistente sin interrumpir el servicio ni requerir que detengas tu aplicación.

Scale-to-Zero (Auto-suspend)

{{ app_name }} monitorea la actividad de cada aplicación cada 60 segundos. Si una app no recibe ninguna petición HTTP en 10 minutos (configurable con MYPAAS_SUSPEND_TIMEOUT_MINS), el proceso hijo se termina y su estado pasa a Suspended.

Cuando un visitante accede al subdominio de una app suspendida, el proxy inverso:

  • Detecta que el proceso no está corriendo.
  • Lanza el binario nuevamente con todas sus variables de entorno.
  • Espera 500ms para que el proceso se inicialice.
  • Reenvía la petición original de forma transparente.
Consejo: Para minimizar el tiempo de arranque en frío, asegúrate de que tu app empiece a escuchar en $PORT lo antes posible, idealmente antes de cargar datos o inicializar la base de datos. Una app Axum mínima arranca en menos de 100ms.

Esta funcionalidad permite alojar muchas apps en un VPS pequeño: los procesos sin tráfico no consumen memoria.
